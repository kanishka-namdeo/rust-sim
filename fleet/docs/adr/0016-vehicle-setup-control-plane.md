# ADR 0016: The QGC/Mission-Planner-style vehicle-setup control plane

**Status**: Accepted (v0.2)
**Context**: Operators configure vehicles in QGroundControl / Mission
Planner through a standard workflow: connect → full parameter download →
pick an airframe → calibrate sensors → set power and safety params →
choose flight modes. The fleet stack had none of this: parameters were
write-only (PARAM_SET with echo, used once for the NAV_DLL_ACT arming
gate) and the console exposed no configuration surface at all. Two
protocol gaps blocked the read side entirely:

1. `PARAM_VALUE` (22) was decoded in XML declaration order; PX4 actually
   wires it value-first (f32 @0, count @4, index @6, id[16] @8, type
   @24). Every live echo decoded to a garbage id, so param writes could
   never confirm against PX4 (the F-2 `NAV_DLL_ACT` escalation in the
   run report was this bug visible end-to-end).
2. `PARAM_REQUEST_LIST` (21) / `PARAM_REQUEST_READ` (20) did not exist,
   so there was no way to ask a vehicle for its configuration in the
   first place.

**Decision**:

- **Param cache per link** (`fleet-mavlink::ParamStore`): every decoded
  PARAM_VALUE — solicited download frames *and* unsolicited write echoes
  — lands in a per-link store keyed by param id, with download-progress
  bookkeeping (`received_unique`/`total`, 3 s staleness → `Stalled`,
  re-request heals it: the protocol's own remedy). This is exactly the
  QGC "parameter download" state machine.
- **Golden-pinned wire orders**: PARAM_VALUE (fixed, above), PARAM_SET
  (value f32 @0, targets @4/@5, id[16] @6, type @22 — byte-compared
  against a pymavlink 2.4.49 vector), PARAM_REQUEST_LIST/READ. The
  fixtures live in `tests/golden_mavlink.json`
  (`gen_param_golden.py` regenerates them).
- **Typed param protocol** (the live tests forced it): PX4 v1.16's param
  manager sends INT32 params as their **bit pattern** inside the f32
  field and labels them with the v2 dialect's *wire type* constants —
  REAL32 = **9** (not the v1 enum's 7), INT32 = 6 — and its receiver
  (`mavlink_parameters.cpp:129`) **rejects PARAM_SETs whose param_type
  mismatches**. So `ParamVal` (Real32/Int32) bit-casts both ways:
  `to_wire()` packs ints as bits, `wire_type()` carries the right
  constant, `ParamStore::typed()/get_i32()` decode reads. The legacy
  `set_param(f32)` infers the type from the cache — this retroactively
  fixes the supervisor's own NAV_DLL_ACT write (an INT32 param).
- **Autosave race, waited out**: PX4's param autosave is deferred
  ~300 ms (`autosave.cpp` ScheduleDelayed). An airframe apply that
  restarts immediately after the write echo races the flash and rcS
  boots the OLD airframe. The apply path sleeps 1.2 s (4x the delay)
  between echo-confirm and the restart queue — QGC's equivalent is the
  operator clicking "reboot" a beat after the write.
- **PX4-correct param ids**: v1.16 battery params carry the `BAT1_`
  instance prefix (`BAT1_N_CELLS`, `BAT1_V_EMPTY`, `BAT1_V_CHARGED`,
  `BAT1_R_INTERNAL`) while the warning thresholds stay unprefixed
  (`BAT_LOW_THR`, `BAT_CRIT_THR`, `BAT_EMERGEN_THR`); safety ids
  (`NAV_RCL_ACT`, `NAV_DLL_ACT`, `COM_LOW_BAT_ACT`, `COM_OBL_RC_ACT`,
  `GF_*`, `RTL_RETURN_ALT`) are as-is. The first live run failed on
  `BAT_N_CELLS` not existing — pinned here so nobody re-guesses.
- **Setup-bench mode**: `[fleet] hold_for_setup = true` holds the fleet
  pre-mission at READY and disarmed (phase `SETUP_HOLD`), because the
  configuration workflow's gates (QGC-faithful) require disarm. The run
  ends at `max_time_s` / e-stop like any other.
- **Airframe catalog** (`fleet-cli/src/airframes.rs`, generated by
  `scripts/gen_airframes.py` from the **built** ROMFS of
  PX4-Autopilot v1.16.2): the union of `etc/init.d/airframes` and
  `etc/init.d-posix/airframes` — every SYS_AUTOSTART id rc.autostart can
  resolve, QGC-browser-grouped (Multirotor/Plane/VTOL/Rover/Boat(UVS)/
  Underwater/Other/Simulator). Regenerate after a PX4 bump.
- **REST plane** (spec §3.4 envelope, same shape): 
  `GET /api/airframes`, `GET /api/modes`, `GET /api/vehicles/{i}/setup`
  (Summary: airframe/calibration/power/safety from the live param
  cache), `GET/POST /api/vehicles/{i}/params` (view + write one param),
  `POST …/params/refresh` (start a download), `POST …/airframe`
  (apply+restart), `POST …/calibrate` (MAV_CMD_PREFLIGHT_CALIBRATION
  241 with commander's own v1.16 param matrix: gyro p1=1, accel p5=1,
  quick p5=4, mag p2=1, level p5=2, baro p3=1, airspeed p6=2),
  `POST …/mode` (DO_SET_MODE with fleet-modes-verified words).
- **Airframe apply = QGC's "Apply and Restart"**: PARAM_SET
  `SYS_AUTOSTART` (echo-confirmed; PX4 autosaves to
  `<workdir>/parameters.bson`) → a **controlled restart** of the
  sim+px4 pair. The restart is a manager action, *not* MAV_CMD 246
  (which in SITL just kills px4 — the process-death supervision would
  read it as a fault): `AppState::request_restart(i)` → the supervisor
  run loop drains the queue, `SimCtl::restart_vehicle` drops the pair
  from tracking *before* the kill (so §2.4 never sees it) and respawns
  into the **same workdir** — rcS `param import` loads the persisted
  SYS_AUTOSTART, detects the change, sets SYS_AUTOCONFIG=1, resets
  params and loads the new airframe. The whole pair restarts because
  the interim sim accepts a single HIL TCP connection (ADR-0001).
- **Gates, QGC-faithful**: airframe/calibration writes are rejected
  409 while ARMED; calibration is further rejected while PX4's
  worker thread is busy (PX4 itself answers TEMPORARILY_REJECTED);
  only catalog SYS_AUTOSTART ids are accepted (422 otherwise).
- **Honesty flag** (`dynamics_compatible`): the interim HIL sim is a
  6-DOF quadrotor, so Multirotor/Simulator airframes are
  physics-compatible; Boat/UUV/Plane/VTOL/Rover airframes configure
  correctly at the parameter level but will not fly correctly against
  the quad dynamics until the real rustsitsim per-airframe models land
  (ADR-0001's deferral). The console surfaces this rather than hiding
  it — the repo's LIVE/SIMULATED rule applied to airframes.

**Consequences**: the console gains a Vehicle Setup tab that is a
thin view over live vehicle state (nothing client-side authored —
param-derived sections read from the vehicle's own PARAM_VALUE cache,
so the view is always the truth). The F-2 NAV_DLL_ACT "write
unconfirmed" escalation disappears (the wire-order fix makes every
write echo-confirmed). Calibration state is observable: CAL_*_ID
params flip nonzero after a calibration run and the next param
download shows it. USV (Boat 1070) and UUV frames are selectable
end-to-end; their flight dynamics remain quad-grade until ADR-0001's
successor lands.
